# Medarot-P

- 「Medarot-P」は、ゲームシリーズ「メダロット」のバトルシステム(ロボトル)を模倣したゲームです。
- 原作の仕様が明確でないため、完全再現を目指すものではありません。独自要素を含みます。
- Pythonを採用し、バイブコーディングによって製作しています。
- ライブラリとしてPygame-CEを利用しています。

---

# アーキテクチャ戦略

本プロジェクトでは、シーンの特性に応じて最適な設計パターンを使い分ける。
パフォーマンス向上のために行数が増えるような最適化は避け、可読性と非冗長性を重視する。

### 1. 動的なシーン（Battle, Map探索など）
多数のオブジェクトが相互作用し、リアルタイムに状態が変化するシーンでは **ECS (Entity Component System)** を採用。

*   **採用理由**:
    *   状態（Component）と振る舞い（System）を分離することで、複雑な相互作用を管理しやすくするため。
    *   「新しいスキル」や「新しいマップギミック」などの機能拡張に対し、既存コードへの影響を最小限にするため。
*   **構成要素**:
    *   `components/`: 純粋なデータクラス。メソッドは持たない。
    *   `systems/`: ロジックの実行者。コンポーネントを操作し、副作用（状態更新、描画）を適用する。
    *   `mechanics/`: 判断ロジック。システムから呼び出され、計算結果のみを返す（純粋関数的アプローチ）。

### 2. 静的なシーン（Title, Customizeなど）
UI操作が主体で、状態遷移が予測可能なシーンでは **MVP (Model-View-Presenter) ライクな分離** を採用。

*   **採用理由**:
    *   ECSのボイラープレート（Component/System定義）を避け、開発速度と可読性を優先するため。
*   **構成要素**:
    *   `Manager` (Model/Presenter): カーソル位置管理、データの読み書き、画面遷移の判断。
    *   `Renderer` (View): 受け取ったデータを描画するだけ。ロジックは持たない。

# ECS設計原則 (Battleシーン詳細)

拡張性を最優先とし、「判断（データ生成）」と「実行（副作用）」を厳格に分離。

1.  **Component (`components/`) = 純粋データ**
    *   状態（フィールド）のみを保持するデータクラス。
2.  **System (`systems/`) = 進行と副作用の実行者**
    *   ゲームループを回す「土管」。
    *   Mechanicsに「何が起きるか」を問い合わせ、その結果をWorldに適用する責務を持つ。
    *   フェーズ遷移、ログ追加、エンティティ生成/削除はSystemのみが行う。
3.  **Mechanics (`battle/mechanics/`) = 判断と計算の専念者**
    *   具体的なゲームルールの実装。
    *   **原則として副作用を持たない**。計算結果（ResolutionResultなど）を返すことに徹する。
4.  **ViewModel / Renderer (`ui/`) = 描画**
    *   **ViewModel**: ECSの世界から情報を収集し、描画用Snapshot（DTO）を生成する。
    *   **Renderer**: Pygameへの描画命令のみを行う。

# ゲームルール概要

*   **チーム**: 3vs3の団体戦。リーダー機の頭部破壊で決着。
*   **戦闘システム**:
    *   「コマンド選択 -> 充填(Charge) -> 行動実行 -> 放熱(Cooldown)」のサイクル。
*   **特性と相性**:
    *   メダル属性とパーツ属性の一致ボーナス。
    *   3すくみ（スピード > パワー > テクニック）による補正。
